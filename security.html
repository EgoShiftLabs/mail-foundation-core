Security & Trust

Caution is healthy.

“Connecting a wallet to an unfamiliar application should make you cautious.

We think that caution is healthy.”

What signing in is

A signature proves ownership. Nothing else.

$MAIL uses signed-message authentication to prove wallet ownership. Your wallet signs a human-readable challenge message — a message signature, never a transaction.

Signing in does NOT:

  • transfer SOL
  • transfer tokens
  • approve token spending
  • submit an asset-transfer transaction
  • reveal a private key
  • reveal a seed phrase

The two rules that matter most

$MAIL never requires a seed phrase or private key. No screen, prompt, email, DM, or “support agent” associated with $MAIL will ever legitimately request them. Anything that does is an attack.

V1 does not custody assets. There is no code path in V1 that holds, moves, or approves movement of any asset — no custody, no token functionality, no payment flow. If a wallet prompt during $MAIL sign-in ever asks you to approve a transaction rather than sign a message, stop and report it.

The architecture

Security controls in the V1 design.

Unpredictable challenges

Authentication challenges use cryptographically unpredictable nonces.

Wallet-bound auth

Each challenge is bound to the requesting wallet — a challenge for one wallet cannot authenticate another.

Challenge expiration

Challenges are short-lived and expire if unused.

Single-use consumption

A challenge is consumed atomically on use. Replaying it — even concurrently — fails.

Server-side verification

ed25519 signatures are verified on the server, never trusted from the client.

Replay resistance

Consumed challenges are rejected; tampered or forged sessions are rejected.

Cross-wallet isolation

Every mailbox read and mutation is scoped to the authenticated session wallet.

Blocking & reporting

Blocked senders are refused (RETURN TO SENDER); recipients can report messages and senders.

Input validation

Wallets, identifiers, folders, and payloads are strictly validated; malformed input fails safely.

Rate limiting

Layered per-IP and per-wallet limits on authentication, sending, reporting, and blocking.

Enumeration resistance

The API does not reveal whether an arbitrary wallet has ever used $MAIL or has mail waiting.

Safe error handling

A central error handler returns generic responses — no stack traces, no internal detail.

Testing

Tested adversarially. Claimed honestly.

36 / 36 internal adversarial security test scenarios are passing after remediation.

This is not an independent third-party security audit. The testing was performed internally by the maintainers using a rerunnable adversarial harness with disposable, zero-asset keypairs. No external certification is claimed. Independent technical review is welcome.

The full findings, the claim-by-claim test matrix, and the harness itself are published in the repository:

  • SECURITY_AUDIT_V1.mdThe adversarial review: findings, remediations, and residual-risk notes.
  • SECURITY_TEST_MATRIX_V1.mdEvery security claim mapped to a test scenario and its result.
  • SECURITY.mdThe security policy and how to report a vulnerability responsibly.
