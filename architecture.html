Architecture

Simple in front.
Careful underneath.

How a signed message becomes a session, and how a letter moves from addressed to opened — as implemented in the current V1 source.

System path

From wallet to data store.

User walletPhantom, Solflare, or another supported Solana wallet.
↓
Signed auth challengeThe server issues a random, single-use, expiring challenge bound to the wallet. The wallet signs the message — never a transaction.
↓
Auth verificationThe server verifies the ed25519 signature against the wallet's public key and consumes the challenge atomically.
↓
Wallet-bound sessionAn HMAC-signed, HTTP-only session cookie scoped to that wallet.
↓
$MAIL APIEvery route validates input and authorizes against the session wallet.
↓
Message / safety / state layerFolder placement, approved senders, blocking, reporting, link detection, delivery-state transitions.
↓
Data storePostgreSQL with parameterized queries only.
Letter lifecycle

Addressed → Delivered → Opened.

SenderAn authenticated wallet writes a letter.
↓
Recipient wallet addressAny valid Solana address — the recipient need not have used $MAIL.
↓
AddressedThe system accepts the correspondence. Placement respects the recipient's rules: approved senders reach the Mailbox, unknown senders land in Requests by default, blocked senders are refused.
↓
Recipient authenticatesThe owner proves control of the wallet with a signed message.
↓
DeliveredRecorded only when the authenticated recipient actually reaches their mail on a $MAIL surface.
↓
Recipient opensAn explicit action by the recipient.
↓
OpenedRecorded only after that explicit open. Only the real recipient can advance these states.
Where the mail lives: normal V1 correspondence is stored by the $MAIL service and is not presented as on-chain messaging. The blockchain's role in V1 is identity: wallet addresses and the signatures that prove ownership of them.
The V1 stack

Contract-first, validated at every boundary.

Frontend

React + Vite single-page app with wallet-adapter connections and typed API hooks generated from the OpenAPI contract.

API

Express 5 with Zod-validated input and output generated from the same OpenAPI spec — one contract, enforced on both sides.

Database

PostgreSQL via Drizzle ORM. Parameterized queries only; every read scoped to the session wallet.

Safety layer

Layered rate limiting, payload caps, strict identifier validation, security headers, and a central generic error handler.

The full architecture notes live in the repository: docs/V1_ARCHITECTURE.md and docs/SECURITY_NOTES.md.
